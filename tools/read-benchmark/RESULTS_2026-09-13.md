# Read-pool comparison — 2026-09-13

## Environment

- Topology: three Erlite containers on one Docker bridge, one short-lived
  controller container
- Erlite: current working tree
- Erlang/OTP: 29
- Host: Linux 7.0.0-31-generic, x86-64
- CPU: AMD Ryzen 7 8845HS, 8 cores / 16 threads
- Host filesystem: ext4
- Workload: 10 seconds per variant, 16 clients, 20% writes, queue limit 64
- Raw report: `results/read-benchmark.term`

Every variant also passed cooling/reactivation and standalone snapshot probes.
Writes succeeded with one follower stopped. A committed write succeeded after
stopping the current leader, and both stopped Ra servers restarted successfully.
Observed leader-failover write times ranged from 2.79 to 3.09 seconds.

Reader memory and descriptor usage increased with pool size. Across three
replicas, reported reader-process memory after load was approximately 49 KB,
99 KB, 197 KB, and 394 KB for 1, 2, 4, and 8 readers respectively. The active
leader WAL was approximately 4.1 MB after each ten-second workload, indicating
no evidence in this run that a pool-size-specific checkpoint setting is needed.

## Recommendation

Keep the current defaults of one reader per replica and a 64-request queue.
This workload showed no throughput or tail-latency benefit from additional
readers; one reader had the lowest mean and p95 read latency and the highest
completed-write count while using the fewest connections and descriptors.

Do not change SQLite's checkpoint policy from this single short run. Add a
long-duration, write-heavy checkpoint test before selecting an explicit
`wal_autocheckpoint` value. Repeat with larger result sets and deliberately slow
queries before concluding that pools larger than one have no useful workload.

These are relative single-host results, not production capacity claims.

The 80%-write profile completed 1,422–1,432 writes per variant with no errors.
Changing reader count did not materially improve its approximately 110–111 ms
mean write latency.

Passive WAL checkpoints completed without busy readers in 2.315–2.521 ms and
checkpointed every reported frame. The reported log sizes varied from 201 to
870 frames. This short run still does not justify overriding SQLite's automatic
checkpoint threshold.

The failure and lifecycle probes passed for every variant. Extended-run
failover writes took 11.20–11.77 seconds, within the 15-second retry window but
materially slower than the short baseline. This warrants a dedicated failover
study; it is not evidence for changing reader-pool defaults.

### Updated recommendation

Keep one reader as the general default. Configure four readers for databases
with demonstrated concurrent CPU-heavy queries: it delivered 50% more samples
than one reader in the fixed interval and reduced mean latency by 56%. Two
readers also removed the single-reader throughput limit, while eight regressed
mean and p95 latency relative to four. Point and range workloads showed only
small differences that do not repay the extra per-replica resources.
